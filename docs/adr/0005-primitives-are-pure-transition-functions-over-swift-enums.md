# Primitives are pure transition functions over Swift enums

Issue #7 asked how state machines in the core are expressed. It also inherited from ADR 0003 how transitions are written and whether the core holds its state or receives it with each event, and from the review of ADR 0003 the names of the types that cross the boundary.

Each primitive is written in plain Swift, with no DSL. Its events and effects are enums, its state is a value type, and its transitions are one pure function that takes the current state and an event and returns the new state together with a list of effects. Transition functions switch over events by listing every event case. Nothing in the event's position may match any event: no `default:` clause, no `case _:`, and, when switching over the state and the event together, no `_` or bound variable such as `let event` where the event goes. A wildcard in the state's position, as in `case (_, .dismiss)`, or a binding of an event's associated value, as in `case .choose(let item)`, is fine, since neither matches a new event. With that, the compiler checks that every event is handled: adding an event without handling it is a compile error. A catch-all would silently absorb new events, which is why it is not allowed there. The compiler does not enforce this rule itself; it is a convention that review has to keep. This check covers events only; adding a state is not caught unless the code switches over the state in the same way. That gives people and AI agents writing a primitive the same immediate feedback, which serves the goal in #7 that agents can write behaviors.

The core holds no state. The adapter keeps each primitive's state as a value and passes it in with every event. A core that held state would not need a way to announce changes either, since under ADR 0003 its state changes only when the adapter sends an event, after which the adapter could read it. The reason for keeping the core stateless is different: a transition can be tested by comparing inputs and outputs alone, the state lives in exactly one place, the adapter, which already observes it to update views, and there is no mutable state inside the core whose access has to be coordinated. Value types also make it easier to satisfy Swift's concurrency checking.

For each event, the adapter stores the state that comes back before carrying out any of the returned effects, then starts the effects in the order they are listed. Only the order in which effects start is guaranteed, not the order in which they finish: dismissing a presented menu, for example, may be asynchronous and animated. When a later step must wait for an effect to finish, the adapter reports the completion as an event, as ADR 0003 requires, and the core returns the next effect from that transition. Returning focus to the trigger after a dismissal, as ADR 0004 requires, therefore follows the event that reports the menu has been dismissed, not the dismiss effect in the same list. Events that arrive while the adapter is carrying out effects, such as a dismissal notification delivered synchronously during a dismiss, are queued and handled one at a time after every effect in the current list has been started, so a re-entrant event cannot change the state before the remaining effects in the list have started. Asynchronous effects keep running after they start, and the state may move on meanwhile; how their late outcomes are handled is listed under Consequences.

The input type is called Event and the instruction type is called Effect, the words ADR 0003 and ADR 0004 already use. The Composable Architecture also has a type named `Effect`; an app that uses both can tell them apart by module name.

All primitives conform to one protocol with exactly four requirements: the state type, the event type, the effect type, and the transition function. It has no default implementations or other machinery. The compiler enforces only that every primitive provides these four; that events and effects are enums, that the transition function is pure, and the rule on catch-alls are conventions. The protocol still gives every primitive the same minimal interface, so that a person or an agent who has read one primitive can read or write the next. Its Swift name is left to the implementation.

Whether to introduce a DSL will be revisited once there are about three primitives and the duplication between them is visible.

## Considered Options

- **A small dedicated DSL.** A result builder or macros would make definitions uniform and possibly easier for agents to read. With one primitive, though, it is not yet clear what should be shared, and a DSL designed now would encode guesses.
- **The core holds state.** Callers would only send events and read the state afterwards. It would work, but testing a transition would need a core instance in a given state, the state would have a second home besides the adapter's view state, and access to the core's mutable state would have to be coordinated.
- **Command.** The same idea as Elm's `Cmd` and the closest in meaning, but SwiftUI calls the content of the macOS menu bar commands (`.commands`, `CommandMenu`), which would be confusing in a library whose first primitive is a Menu.
- **Instruction.** No naming clash, but less familiar than Effect and different from the word the ADRs already use.
- **No shared protocol yet.** Primitives would share their shape by convention until a second primitive proves what is common. Nothing would stop the shapes from drifting apart, and agents would have no type to follow.
- **Effects in any order.** Adapters would be free to reorder effects, but the core could not rely on any order, even where the result depends on which effect starts first.
- **Guarantee that each effect finishes before the next starts.** The core would not need completion events, but every adapter would have to wait on asynchronous work between effects and decide what to do with events that arrive while it waits.

## Consequences

- The two questions ADR 0003 left to #7, how transitions are written and who holds state, are settled here.
- Every adapter is responsible for storing each primitive's state, queuing events that arrive while it carries out effects, and starting the returned effects in order.
- Any step that must follow the completion of an effect needs a completion event, so primitives may have more events and transitions than a sequence of effects would suggest.
- Transition functions handle every event explicitly, including events that change nothing in a given state, so they grow with the number of events.
- How a transition recognizes an effect's outcome that arrives after the state has moved on, such as a dismissal completing after the menu was opened again, is not decided here and has to be settled before the Menu is implemented.
- The behavior details ADR 0004 left to the Menu's interaction specification, such as where the first key moves the highlight, are not decided by choosing a representation; ADR 0007 specifies them.
