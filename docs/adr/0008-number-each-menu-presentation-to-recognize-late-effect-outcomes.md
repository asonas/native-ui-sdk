# Number each menu presentation to recognize late effect outcomes

Issue #18 asked how a transition recognizes an effect's outcome that arrives after the state has moved on. ADR 0005 guarantees only the order in which effects start, so a report that the menu has been dismissed, or the outcome of returning focus to the trigger, can arrive after the menu has been opened again. ADR 0007 left three points with this question: when a menu opened again starts accepting choices, how a choice that has taken effect still has its action requested exactly once, and how the reopened menu's focus is protected from a focus return still under way.

Once the core knows the menu is closing or closed, an open operation is accepted, even while the previous presentation's dismissal or focus return is still under way. A presentation is one showing of the menu, started by an accepted open operation. The core knows the menu is closing from the moment it returns a dismiss effect, after Escape, a choice, or focus leaving the menu, and it learns of a dismissal the system makes on its own only from the report that the menu has closed. An open operation that arrives while the core still considers the menu open does nothing, so the adapter reports a system dismissal as soon as it observes one.

Each accepted open operation advances a presentation number kept in the core's state; transitions are pure (ADR 0005), so the transition that opens the menu advances it. The number identifies that presentation and everything that belongs to it, including reports delivered after it has closed: the effects to dismiss the menu and to return focus to the trigger carry it, and the adapter attaches it to the events reporting their outcomes. Every report that a presentation has closed carries its number too, whether the menu closed through the core's dismiss effect, through Escape, by the system, or through an outside tap. The adapter takes the number when it shows a presentation and uses that number, not whatever the state holds by the time it reports, for everything that presentation reports later. The core only compares numbers for equality, so a number must not be used again while a report about the presentation it belonged to can still arrive; a counter as wide as a 64-bit integer does not come back around in practice. User operations inside the menu, such as moving to the next item or choosing one, carry no number to the core. The adapter remembers which presentation each such operation came from, including while it waits in the queue (ADR 0005), and passes it to the core only if that presentation's number matches the number in the latest state; operations from an earlier presentation still on screen are dropped, so an operation always applies to the presentation the core has open. Open operations from the trigger are not checked this way.

A report about the current presentation is handled as ADR 0004 and ADR 0007 describe. A report about an earlier presentation never changes the menu that is open: it does not close it, does not move its highlight, and does not lead to a new request to return focus to the trigger, which would take focus away from the reopened menu. A second closed report for a presentation whose closing the core has already handled, for example one from the dismiss effect finishing and another from the system, is ignored in the same way, whether or not the menu has been opened again.

If the menu is opened again after a choice has taken effect but before its action has been requested, the transition that opens the menu also returns the effect to perform the chosen item's action. Reopening issues no new request to return focus for the earlier presentation; a request already issued cannot be taken back (ADR 0004) and may still complete, but the action no longer waits for its outcome, since the reopened menu is where focus belongs now. Whichever comes first requests the action: the reopening, or the report after which ADR 0007 requests it, which is normally the focus return's outcome and, after the user acted outside, the closed report. The other then finds nothing pending, so the action is never requested twice. Since no earlier choice is left waiting, the reopened menu accepts choices at once. The cost is that an action that presents a sheet or alert can do so while the reopened menu is shown or about to be shown; the user, having opened the menu again right after choosing, has already moved on.

Every focus return now reports its outcome, success or failure, not only the one after a choice as ADR 0007 required. If a focus return for an earlier presentation reports success while a later presentation is open, the return may have moved focus to the trigger after the reopened menu took it, so the core returns an effect to move focus back into the menu, as the adapter does when the menu opens (ADR 0004). That effect carries the number of the presentation it is for, and the adapter moves focus only if that presentation is still the one open when it carries the effect out. A failed return moved no focus and needs nothing, and if the menu has closed again by the time the outcome arrives, the outcome changes nothing. Focus that leaves an open menu because a focus return for an earlier presentation moved it was moved by an effect, not by the user; as with the dismiss effect in ADR 0007, the adapter does not report it as focus leaving the menu, so the open menu is not closed before focus can be moved back into it.

Once the core knows a presentation is closing, an open operation is never refused because that presentation is unfinished, so a report that never arrives about it cannot leave the menu impossible to open. A lost report of a dismissal the system made on its own is different: the core still considers the menu open, and open operations do nothing until the adapter reports the closing. The adapter still has to report every closed presentation and every focus return's outcome: an action waiting on a lost report is requested if the menu is opened again, and otherwise not at all. The core treats the dismiss effect as always closing the presentation in the end and adds no event for a dismissal that fails; whether a SwiftUI presentation can fail to close, and what the adapter then does, is checked when the Menu is implemented.

Whether SwiftUI can present the menu again while the previous presentation is still animating out has not been checked either. The rules above hold either way: if the adapter has to wait before showing the new presentation, that wait is the adapter's job, and the core already treats the menu as open.

## Considered Options

- **Refuse to open the menu until the previous presentation's reports have arrived.** The state alone would tell outcomes apart, with no numbers, but a single lost report would leave the menu impossible to open, a click during the closing animation would do nothing, and the adapter would have to guarantee one closed report per presentation.
- **Remember the open operation and open the menu once the previous presentation's reports have arrived.** No click is lost, but opening is delayed, and a lost report still leaves the menu unopened.
- **Tag each effect with its own identifier.** More general, but a presentation has at most one dismissal and one focus return outstanding, so the presentation's number already tells their outcomes apart with less state.
- **Number user operations as well.** The core could reject operations from an earlier presentation itself, but every operation would carry a number that only matters while two presentations overlap on screen, which the adapter can already tell apart.
- **Request a pending action when the earlier presentation reports it has closed, and refuse choices in the reopened menu until then.** The action would not appear over the reopened menu, but a lost report would leave the reopened menu unable to choose anything.
- **Request a pending action when the earlier presentation reports it has closed, and accept choices in the reopened menu meanwhile.** Nothing is refused, but the state would have to hold two chosen items waiting for their actions and an order between them.
- **Do nothing when an earlier focus return finishes after the menu reopened.** Simpler, and focus returns usually finish quickly, but when it happens, key input stops reaching the open menu, which ADR 0004 requires.
- **Refuse to open the menu until a focus return under way has reported its outcome.** Protects the reopened menu without a new effect, but a lost outcome would leave the menu impossible to open.

## Consequences

- The Menu's state includes a presentation number. The effects to dismiss the menu, to return focus, and to move focus back into the menu, and the events reporting that the menu closed and that a focus return succeeded or failed, carry it.
- The Menu gains an effect to move focus back into the menu, which every adapter has to carry out (ADR 0003).
- Reporting a focus return's outcome is required after every focus return, which revises ADR 0007's consequence that it was optional for dismissals other than after a choice.
- The adapter keeps track of which presentation it is showing: it drops operations from inside an earlier one, uses each presentation's own number in its reports, and does not report focus moved by a focus return as focus leaving the menu.
- An open operation that arrives while a system dismissal is under way but not yet reported does nothing, so how early the adapter can report a system dismissal decides how soon the menu can be opened again, and a lost report of one leaves the menu unopenable, which opening again cannot recover.
- An action whose choice was followed quickly by reopening the menu is requested when the menu reopens, so what it presents can overlap the reopened menu, and focus moved back into the menu after a late focus return can take focus from what that action presented.
- Whether the SwiftUI adapter has to delay showing a presentation while the previous one is animating out, and whether a SwiftUI presentation can fail to close, are found out when the Menu is implemented; #15 tracks them.
- Other effects whose outcomes arrive later, such as a timer if the Menu uses one, can be told apart by the same kind of number; whether the Menu needs a timer is not decided here.
