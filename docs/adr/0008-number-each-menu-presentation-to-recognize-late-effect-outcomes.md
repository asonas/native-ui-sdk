# Number each menu presentation to recognize late effect outcomes

Issue #18 asked how a transition recognizes an effect's outcome that arrives after the state has moved on. ADR 0005 guarantees only the order in which effects start, so a report that the menu has been dismissed, or the outcome of returning focus to the trigger, can arrive after the menu has been opened again. ADR 0007 left three points with this question: when a menu opened again starts accepting choices, how a choice that has taken effect still has its action requested exactly once, and how the reopened menu's focus is protected from a focus return still under way.

An open operation is accepted whenever the menu is not open, even while the previous presentation's dismissal or focus return is still under way. A presentation is one showing of the menu, from the operation that opens it until it is reported closed. Each time the menu opens, the core increments a presentation number kept in its state; transitions are pure (ADR 0005), so the core cannot make up identifiers any other way. The effects to dismiss the menu and to return focus to the trigger carry the number of the presentation they belong to, and the adapter attaches that number to the events reporting their outcomes. Every report that a presentation has closed carries its number too, whether the menu closed through the core's dismiss effect, through Escape, by the system, or through an outside tap. The adapter reads the number of each presentation from the state. The core only compares numbers for equality, so a number that wraps around after many presentations causes no harm. User operations, such as moving to the next item, carry no number: they reach the presentation on screen and are handled in the order they arrive (ADR 0005).

A report about the current presentation is handled as ADR 0004 and ADR 0007 describe. A report about an earlier presentation never changes the menu that is open: it does not close it, does not move its highlight, and does not lead to focus being returned to the trigger, which would take focus away from the reopened menu. A second closed report for a presentation whose closing the core has already handled, for example one from the dismiss effect finishing and another from the system, is ignored in the same way, whether or not the menu has been opened again.

If the menu is opened again after a choice has taken effect but before its action has been requested, the transition that opens the menu also returns the effect to perform the chosen item's action, exactly once. Focus is no longer returned for the earlier presentation, and if a focus return is already under way, the action no longer waits for its outcome; the reopened menu is where focus belongs now. Since no earlier choice is left waiting, the reopened menu accepts choices at once. The action is requested even if the report the earlier presentation was waiting for never arrives, so a lost report cannot lose the action. The cost is that an action that presents a sheet or alert does so while the reopened menu is on screen; the user, having opened the menu again right after choosing, has already moved on.

Every focus return now reports its outcome, success or failure, not only the one after a choice as ADR 0007 required. If a focus return for an earlier presentation reports success while a later presentation is open, the return may have moved focus to the trigger after the reopened menu took it, so the core returns an effect to move focus back into the menu, as the adapter does when the menu opens (ADR 0004). A failed return moved no focus and needs nothing. If the menu has closed again by the time the outcome arrives, the outcome changes nothing.

Since an open operation is never refused because of an unfinished presentation, a report that never arrives cannot leave the menu impossible to open. The adapter still has to report every closed presentation and every focus return's outcome; an action that was waiting on a lost report is requested when the menu is opened again, and otherwise not at all. This ADR adds no event for a dismissal that fails: the adapter reports that a presentation has closed once it is no longer on screen.

Whether SwiftUI can present the menu again while the previous presentation is still animating out has not been checked. The rules above hold either way: if the adapter has to wait before showing the new presentation, that wait is the adapter's job, and the core already treats the menu as open.

## Considered Options

- **Refuse to open the menu until the previous presentation's reports have arrived.** The state alone would tell outcomes apart, with no numbers, but a single lost report would leave the menu impossible to open, a click during the closing animation would do nothing, and the adapter would have to guarantee one closed report per presentation.
- **Remember the open operation and open the menu once the previous presentation's reports have arrived.** No click is lost, but opening is delayed, and a lost report still leaves the menu unopened.
- **Tag each effect with its own identifier.** More general, but a presentation has at most one dismissal and one focus return outstanding, so the presentation's number already tells their outcomes apart with less state.
- **Request a pending action when the earlier presentation reports it has closed, and refuse choices in the reopened menu until then.** The action would not appear over the reopened menu, but a lost report would leave the reopened menu unable to choose anything.
- **Request a pending action when the earlier presentation reports it has closed, and accept choices in the reopened menu meanwhile.** Nothing is refused, but the state would have to hold two chosen items waiting for their actions and an order between them.
- **Do nothing when an earlier focus return finishes after the menu reopened.** Simpler, and focus returns usually finish quickly, but when it happens, key input stops reaching the open menu, which ADR 0004 requires.
- **Refuse to open the menu until a focus return under way has reported its outcome.** Protects the reopened menu without a new effect, but a lost outcome would leave the menu impossible to open.

## Consequences

- The Menu's state includes a presentation number. The effects to dismiss the menu and to return focus, and the events reporting that the menu closed and that a focus return succeeded or failed, carry it.
- The Menu gains an effect to move focus back into the menu, which every adapter has to carry out (ADR 0003).
- Reporting a focus return's outcome is required after every focus return, which revises ADR 0007's consequence that it was optional for dismissals other than after a choice.
- An action whose choice was followed quickly by reopening the menu runs while the reopened menu is on screen, and focus moved back into the menu after a late focus return can take focus from what that action presented.
- Whether the SwiftUI adapter has to delay showing a presentation while the previous one is animating out is found out when the Menu is implemented.
- Other effects whose outcomes arrive later, such as a timer if the Menu uses one, can be told apart by the same kind of number; whether the Menu needs a timer is not decided here.
