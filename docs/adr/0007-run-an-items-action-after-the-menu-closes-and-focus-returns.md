# Run an item's action after the menu closes and focus returns

Issue #17 asked for the parts of the Menu's interaction that ADR 0004 left to its specification, who carries out an item's action and when, and whether the standard menus on macOS and iOS treat disabled items as WAI-ARIA does.

A choose operation reaching the core is not yet a choice. The choice takes effect only if the item the operation names still exists and is enabled; otherwise nothing happens and the menu stays open, as ADR 0004 requires. When a choice takes effect, the transition returns a state that records the chosen item, together with an effect to dismiss the menu. Further choose operations that reach the menu being dismissed do nothing, so a second choice cannot replace the first or dismiss the menu twice. A menu opened again before the first choice's action has been requested accepts choices at once, since ADR 0008 has that opening request the pending action.

Once the adapter reports that the menu has been dismissed, the core returns an effect to return focus to the trigger, as ADR 0004 requires. After the adapter reports that the focus return succeeded or failed, for whatever reason, the core returns an effect to perform the chosen item's action, exactly once. ADR 0005 guarantees only the order in which effects start, so returning both effects at once would let a focus return that finishes late take focus away from a sheet the action has just presented; waiting for the outcome follows ADR 0005's rule that a step which must follow an effect's completion waits for an event reporting it. The core does not know what the action does: the effect identifies the choice, and the adapter performs the action that was attached to the item when the choice took effect. The adapter keeps that action until it is performed, so the action still runs if the item disappears, or is replaced by another item with the same identity, before the menu has finished closing. The choice was made while the item existed; an item that vanishes before the choice takes effect is not chosen at all, as ADR 0004 requires. Because the focus return has finished, one way or the other, before the action starts, an action that moves focus elsewhere, for example into a sheet it presents, has the last word. This ordering, and those in the next two paragraphs, hold as long as the menu is not opened again before the action has been requested; if it is, ADR 0008 has the reopening request the action at once instead, without waiting for any outcome of the earlier presentation.

Other things may happen while the dismissal the core requested after a choice is still under way. The choice still decides that the action is requested exactly once; the other events decide only whether focus is returned first. If the user acts outside the menu before the core has asked for focus to be returned, ADR 0004's rule that focus is not returned wins, and the core requests the action once the menu is reported closed, without asking for focus to be returned; an outside tap that closed the menu can itself be that report. An Escape operation in the meantime changes nothing, since the menu is already being dismissed. Any report that the menu has closed, whether through the core's dismiss effect, through Escape, or by the system, is the dismissal the core was waiting for: unless the user acted outside first, the core asks for focus to be returned and requests the action after the outcome of that return. Once the core has asked for focus to be returned, the request cannot be taken back (ADR 0004), so a later action outside the menu does not change it, and the action still follows the return's outcome. Focus that leaves the menu because the dismiss effect closed it is part of that dismissal, and the adapter does not report it as focus leaving the menu.

If the trigger no longer exists when focus is to be returned, for example because something else in the app removed it while the menu was open, the adapter reports that focus could not be returned, the core still requests the action once, and it does nothing further about focus. Where focus goes then is up to the app, which is the one that removed the trigger. An action that removes the trigger does not reach this case, since it runs after the focus return has finished; moving focus somewhere sensible is then the action's job.

When nothing is highlighted, the operation that moves to the next item highlights the first item it can reach, and the operation that moves to the previous item highlights the last. The WAI-ARIA Menu Button pattern does this when the menu is opened from its button with the Down or Up Arrow; applying it to an open menu with nothing highlighted is this project's choice. When the pointer leaves an item for a part of the menu with no item, or leaves the menu, the highlight clears; when it moves onto another item, the highlight moves there. When the highlighted item disappears while the menu is open, the highlight clears, and the next movement starts as if nothing had been highlighted. Clearing the highlight, rather than moving it to a neighbor, is in the spirit of ADR 0004's rule that no other item is silently put in the vanished item's place: a choose operation chooses nothing until navigation highlights an existing item.

ADR 0004 let disabled items be highlighted, following WAI-ARIA, and noted that the standard menus on Apple platforms had not been checked. Checking on macOS showed that the standard menu skips disabled items when the arrow keys move the highlight. The core therefore offers two forms of each operation that moves the highlight from the keyboard: one that includes disabled items and one that moves only between enabled items. Only the arrow keys were checked; giving the same two forms to opening the menu with the first item highlighted and to typeahead follows from that observation, so that a keyboard user on macOS never lands on a disabled item. When no item is enabled, the enabled-only form highlights nothing. Which form a key maps to is the adapter's choice, made per platform as ADR 0003 requires; the macOS adapter uses the enabled-only form. Whether the pointer resting on a disabled item highlights it is also the adapter's choice: an adapter that should not highlight it reports that the pointer left the item. When VoiceOver moves onto a disabled item, that item is highlighted on every platform, since VoiceOver moves on its own and its user needs to hear which item they are on. Choosing a disabled item still does nothing, whichever operation put the highlight there.

## Considered Options

- **Perform the action when the choice takes effect, before the menu closes.** Simpler, with no waiting for the dismissal, but an action that presents a sheet or alert would do so while the menu is still on screen.
- **Return the focus and action effects together.** One event fewer, but since only their start order is guaranteed, a focus return that finishes late could take focus from what the action presented. Requiring the adapter to finish the return before starting the action would make this one effect an exception to ADR 0005.
- **Perform the action before returning focus.** The action could start without waiting for focus, but returning focus afterwards would override wherever the action moved it.
- **Return focus after a choice whatever closes the menu.** One rule for every cause, but if the user acts outside the menu while it is closing, focus would be pulled back from where they just acted, against ADR 0004.
- **Up and Down both highlight the first item when nothing is highlighted.** Simpler, but the Up Arrow could not reach the last item directly.
- **Keep the highlight on the last item the pointer was over.** A user switching to the keyboard could continue from there, but the menu would show a highlight where the pointer no longer is.
- **Move the highlight to a neighbor when the highlighted item disappears.** Easier to continue from the keyboard, but a choose operation arriving right after the move would choose an item the user's navigation never highlighted, which goes against what ADR 0004's rule is meant to prevent.
- **Clear the highlight but remember where the vanished item was.** The next movement could continue from that position, at the cost of extra state for a rare case.
- **Always skip disabled items.** Matches macOS with less to specify, but keyboard users on other platforms would lose the WAI-ARIA behavior that lets them notice disabled items, which ADR 0004 chose deliberately.
- **Keep ADR 0004 unchanged.** Follows WAI-ARIA everywhere, but on macOS the menu would behave differently from the standard one.
- **Take a fallback focus target from the app.** The adapter could move focus there when the trigger is gone, but this would add API for a rare case that the app already knows how to handle.

## Consequences

- The Menu's state includes the chosen item from the choice taking effect until its action is requested, and the Menu gains an event reporting that focus returned and an effect to perform an item's action. A successful focus return must be reported after a choice; this ADR left reporting success optional for other dismissals that return focus, and ADR 0008 later required it after every focus return.
- The adapter holds the action attached to the chosen item from the choice until it performs it.
- The Menu has more operations: each keyboard movement exists in two forms, and adapters have to pick one per platform.
- How the standard iOS menu treats disabled items under a hardware keyboard has not been checked; the iOS adapter's choice of form waits for that check, which is tracked in #15.
- Whether movement wraps from the last item to the first, and whether Home and End are supported, are not decided here and have to be settled before the Menu is implemented.
- How a transition recognizes a dismissal or focus return reported after the menu has been opened again was left to #18. ADR 0008 decides it: reports carry a presentation number, opening the menu again requests a pending action at once, and a late focus return that succeeds is followed by moving focus back into the reopened menu.
