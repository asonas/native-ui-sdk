# Run an item's action after the menu closes and focus returns

Issue #17 asked for the parts of the Menu's interaction that ADR 0004 left to its specification, who carries out an item's action and when, and whether the standard menus on macOS and iOS treat disabled items as WAI-ARIA does.

A choose operation reaching the core is not yet a choice. The choice takes effect only if the item the operation names still exists and is enabled; otherwise nothing happens and the menu stays open, as ADR 0004 requires. When a choice takes effect, the core records the chosen item in its state and returns an effect to dismiss the menu. Once the adapter reports that the menu has been dismissed, the core returns two effects in this order: return focus to the trigger, then perform the chosen item's action. The core does not know what the action does; the effect names the item, and the adapter performs the action the app attached to it. Because focus returns before the action starts, an action that moves focus elsewhere, for example into a sheet it presents, has the last word. ADR 0005 guarantees only the order in which effects start, so the adapter has to carry out the focus return in a way that a focus move made by the action is not overridden by it. The standard menu on macOS likewise closes before it sends the item's action. Once a choice has taken effect, its action runs even if the item disappears before the dismissal is reported, since the choice was made while the item existed.

When nothing is highlighted, the operation that moves to the next item highlights the first item, and the operation that moves to the previous item highlights the last item, as the WAI-ARIA Menu Button pattern does when its menu is opened with the Down or Up Arrow. When the pointer leaves an item for a part of the menu with no item, or leaves the menu, the highlight clears; when it moves onto another item, the highlight moves there. When the highlighted item disappears while the menu is open, the highlight clears, and the next movement starts as if nothing had been highlighted. Clearing the highlight, rather than moving it to a neighbor, keeps ADR 0004's rule that no other item is silently put in the vanished item's place.

ADR 0004 let disabled items be highlighted, following WAI-ARIA, and noted that the standard menus on Apple platforms had not been checked. On macOS, the standard menu skips disabled items when the arrow keys move the highlight. The core therefore offers two forms of each operation that moves the highlight from the keyboard: one that includes disabled items and one that moves only between enabled items. This covers moving to the next and previous item, opening the menu with the first item highlighted, and typeahead; when no item is enabled, the enabled-only form highlights nothing. Which form a key maps to is the adapter's choice, made per platform as ADR 0003 requires; the macOS adapter uses the enabled-only form. When the pointer moves onto a disabled item, an adapter following macOS can report that the pointer left the item. When VoiceOver moves onto a disabled item, that item is highlighted on every platform, since VoiceOver moves on its own and its user needs to hear which item they are on. Choosing a disabled item still does nothing, whichever form put the highlight there.

If the trigger no longer exists when focus is to be returned, for example because something else in the app removed it while the menu was open, the adapter reports that the effect could not be carried out, as ADR 0004 requires, and the core does nothing further. Where focus goes then is up to the app, which is the one that removed the trigger. An action that removes the trigger does not reach this case, since it runs after focus has returned; moving focus somewhere sensible is then the action's job.

## Considered Options

- **Perform the action when the choice takes effect, before the menu closes.** Simpler, with no waiting for the dismissal, but an action that presents a sheet or alert would do so while the menu is still on screen.
- **Perform the action before returning focus.** An action that removes the trigger would then make the focus return fail visibly, but returning focus afterwards would override wherever the action moved focus.
- **Any key highlights the first item when nothing is highlighted.** Simpler, but the Up Arrow could not reach the last item directly.
- **Keep the highlight on the last item the pointer was over.** A user switching to the keyboard could continue from there, but the menu would show a highlight where the pointer no longer is.
- **Move the highlight to a neighbor when the highlighted item disappears.** Easier to continue from the keyboard, but a choose operation right after would choose an item the user never pointed at, which ADR 0004 rules out.
- **Clear the highlight but remember where the vanished item was.** The next movement could continue from that position, at the cost of extra state for a rare case.
- **Always skip disabled items.** Matches macOS with less to specify, but keyboard users on other platforms would lose the WAI-ARIA behavior that lets them notice disabled items, which ADR 0004 chose deliberately.
- **Keep ADR 0004 unchanged.** Follows WAI-ARIA everywhere, but on macOS the menu would behave differently from the standard one.
- **Take a fallback focus target from the app.** The adapter could move focus there when the trigger is gone, but this would add API for a rare case that the app already knows how to handle.

## Consequences

- The core's state for the Menu includes the chosen item between the choice taking effect and the dismissal being reported, and the Menu gains an effect to perform an item's action.
- The Menu has more operations: each keyboard movement exists in two forms, and adapters have to pick one per platform.
- How the standard iOS menu treats disabled items under a hardware keyboard has not been checked; the iOS adapter's choice of form waits for that check.
- Whether movement wraps from the last item to the first, and whether Home and End are supported, are not decided here and have to be settled before the Menu is implemented.
- How a transition recognizes a dismissal reported after the menu has been opened again is left to #18; the chosen item recorded here is part of the state that question has to consider.
