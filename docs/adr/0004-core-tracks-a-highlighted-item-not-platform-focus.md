# The core tracks a highlighted item, not platform focus

Issue #6 asked which kind of "focus" the core's rules refer to. Apple platforms have at least two kinds that do not move together: keyboard focus, which SwiftUI exposes through `@FocusState`, and accessibility focus, the element VoiceOver is on, which SwiftUI exposes through `@AccessibilityFocusState`. VoiceOver moves its focus between elements on its own, and keyboard focus does not necessarily follow it.

The core tracks neither of them. Instead it tracks the highlighted item: the item in the Menu chosen in #4 that navigation currently points at. Arrow keys, typeahead, the pointer moving over an item, and VoiceOver moving onto an item all reach the core as semantic operations, as ADR 0003 requires, and each of them moves the highlight. Reflecting the highlight in keyboard focus, accessibility focus, or only in how the item is drawn is the adapter's job. Whatever it chooses, two results must hold: after the menu is opened from the keyboard, key input reaches the menu as its operations, and a VoiceOver user can tell which item is highlighted.

When the menu is opened from the keyboard, the first item is highlighted (the first enabled item when the adapter uses the form that skips disabled items, as ADR 0007 revised), as in the WAI-ARIA Menu Button pattern that #4 took as the reference. When it is opened with the pointer or by touch, nothing is highlighted until an operation moves the highlight, so that a pointer user sees no highlight they did not ask for. The pattern does not specify opening with the pointer, so this is this project's choice. If VoiceOver focus moves into the menu, that movement is the operation that sets the highlight.

Disabled items can be highlighted. This follows the WAI-ARIA pattern, which keeps disabled items focusable but not activatable. This ADR originally had moving between items, including the initial highlight, never skip them; ADR 0007 revised that after finding that the standard menu on macOS skips them, so keyboard movement now comes in a form that includes disabled items and a form that skips them, and the adapter picks one per platform. Choosing a disabled item does nothing and leaves the menu open; the pattern does not say this directly, and this project derives it from "not activatable".

If the highlighted item stops existing while the menu is open, a choose operation that arrives before the highlight has moved to an existing item chooses nothing: neither the vanished item nor another item silently put in its place. Where the first key moves the highlight when nothing is highlighted, whether the highlight clears when the pointer leaves an item, and what becomes highlighted after the highlighted item disappears were left to the Menu's interaction specification and are decided in ADR 0007.

When the menu closes because the user dismissed it, for example with Escape or the VoiceOver escape gesture, because the system dismissed it, for example after the user swiped away a menu presented as a sheet, or because the user chose an enabled item, the core returns an effect to return focus to the trigger. When the core itself has to dismiss the menu, as after Escape or a choice, it returns this effect once the adapter reports that the menu has been dismissed, not together with the dismiss effect (ADR 0005); a system dismissal already reports a closed menu, so the effect follows it directly. When the menu closes because the user acted outside it, by tapping or clicking outside it or by moving focus out of it with Tab or VoiceOver ("focus left the menu" in ADR 0003), the menu closes without that effect. If the menu is still presented, as after focus moved out of it, the core moves to the closed state and returns an effect to dismiss it, which the adapter carries out as ADR 0003 requires. Focus is not returned in either case, since the user has moved on to another part of the screen. WAI-ARIA does not specify the outside tap or click; not returning focus is this project's decision.

Some presentations close themselves on an outside tap and report it only as a system dismissal. The adapter determines the cause before reporting the dismissal to the core, because an effect to return focus cannot be taken back once it has been returned. When the adapter knows the menu closed because the user acted outside it, that case wins and focus is not returned. When it cannot tell, it reports a system dismissal and focus is returned. This is a product judgment that weighs the two failures, not a measured result: an unneeded return after a touch is judged less harmful than leaving a keyboard or VoiceOver user with no focus.

Which platform focus the adapter moves to carry out the effect is the adapter's choice. If the trigger no longer exists, for example because something else in the app removed it while the menu was open, the adapter reports that the effect could not be carried out as an event, as ADR 0003 requires; ADR 0007 leaves where focus goes in that case to the app. After a choice, ADR 0007 also has the adapter report a successful return, since the chosen item's action waits for it.

## Considered Options

- **Keyboard focus only.** The core would model `@FocusState`-style focus and leave VoiceOver focus to the accessibility mapping. VoiceOver operations could still move that state, but it would then no longer mean keyboard focus, and its name would mislead about what it tracks.
- **Keyboard and accessibility focus as separate states.** More complete, but the core would have to keep two states consistent with each other and with the platform, which only the adapter can observe.
- **Always highlight the first item on open.** Simpler, and the first key would always have a starting point, but a menu opened by clicking or tapping would show a highlight the user did not ask for.
- **Skip disabled items.** Fewer steps to reach an item that can be chosen, but users moving with the keyboard would be less likely to notice that a disabled item exists.
- **Always return focus to the trigger.** Simpler, but after an outside tap or click it could pull focus away from where the user just acted.
- **Do not return focus when the cause is unknown.** Respects a possible outside tap, but a menu swiped away or otherwise closed by the system could leave keyboard and VoiceOver users with no focus.

## Consequences

- Each adapter decides, per platform, whether keyboard focus, VoiceOver focus, or only drawing follows the highlight, as long as the two required results hold.
- Opening the menu needs two operations, one that opens it with the first item highlighted and one that opens it with nothing highlighted; ADR 0007 gives the first of them a form that highlights the first enabled item. Each adapter decides which platform input maps to which, so the input source itself does not reach the core.
- How reliably focus return follows the user's intent depends on how well each presentation lets the adapter tell an outside tap from other system dismissals.
- How the standard menus on macOS and iOS treat disabled items during keyboard movement had not been checked. The standard menu on macOS turned out to skip them, and ADR 0007 revised this decision accordingly; iOS remains unchecked.
